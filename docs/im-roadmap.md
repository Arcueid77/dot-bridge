## 1.0 要交付什么

面向外部用户发布可自行部署的稳定版本：从零接通自己的 IM 和原来的 dot，长期运行，并完成升级、备份、恢复和迁移。继续采用「独立渠道组件 → 共享 core → 聚合路由 → 官方 Secure MCP Tunnel → 原 dot」结构。

发布渠道先采用 GitHub Release、固定版本源码和可校验发行包。npm registry 发布另行决定，`private: true` 保持到 npm 安装路径和包依赖方案验收完成。

官方 Tunnel 适用于私有 MCP 连接；插件商店公开上架要求稳定、公开可达的 HTTPS MCP 入口。商店上架列为独立后续项目，现有 1.0 保持私有 Tunnel 接法。[官方发行边界](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)

首次接入先核对目标账号／工作区的自定义 MCP 权限和 Tunnel 角色。运行凭据采用 Tunnels Read + Use；创建或管理 Tunnel 的权限单独处理。[官方权限说明](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels#permissions-and-access)

## 1.0 范围

- 飞书、QQ、钉钉、企业微信、微信 iLink、Discord、Telegram、LINE 八渠道均完成基础本人私聊验收；只安装和启用用户选择的渠道。
- 图片、原始音频、转写、文件读取、媒体回复、流式更新、主动发送和定时消息分别列能力及验证状态。各渠道按实际平台权限开放。
- 飞书、Telegram、Discord 的成员白名单／全员、真实 @、关键词／全消息触发和原会话／话题回复纳入回归。其他渠道的群聊扩展进入后续排期。
- Linux x64 和 Windows x64 纳入正式验收；Linux 提供 systemd 常驻，Windows 补齐常驻及退出行为。macOS 标注未验证，欢迎试用并反馈。
- 同一个 dot、同一个既有 Tunnel 和原会话回复保持为默认拓扑。源码、配置、数据和个人凭据分开管理。

## 0.9.0：把已有工具连成完整流程

1. **首次接入向导**：复用现有本机管理界面和 CLI，串起账号资格、依赖检查、平台应用、私有凭据交接、本人配对、原 dot 订阅与实际消息确认。缺少的平台权限和人工步骤一次列出。
2. **常驻与维护**：Linux／Windows 均能查看、启动、停止和恢复服务；明确终端退出、用户退出登录和系统重启后的行为。部署电脑与运行主机可分离。
3. **升级与回滚**：核对全套组件和接口兼容性，处理在途工作，备份后切换并检查状态；失败时恢复上一套兼容代码和配置，保留新收到的数据、去重及发送结果。冻结 1.0 的清单、CLI、MCP schema／错误和数据迁移契约。
4. **完整备份和迁移**：由清单枚举所有选中渠道及其数据库、密钥、配对、订阅、官方 Tunnel profile 和必要 TLS 状态。扩展当前历史双渠道备份脚本，完成加密导出、隔离恢复和新主机切换演练。
5. **可诊断运行**：统一显示平台连接、原 dot 订阅与到期时间、最近投递和队列状态；记录固定错误分类及脱敏平台错误码。续订由原 dot／平台完成，桥侧提供临期状态、失败原因和恢复指引。补齐账号失效、磁盘不足和过载的处理路径。
6. **发行工程与文档**：十个仓库持续验证；总包测试实际安装的八渠道组合。安装、管理、故障处理、备份恢复、能力矩阵和 Agent 部署指引中英文对齐，核对第三方许可证与客户端分发方式。

关键操作保留确认点，普通诊断和可逆准备连续执行。凭据输入、配对和真实订阅逐步接入受保护流程；管理页面继续只监听本机地址。

## 1.0.0-rc：冻结功能并验证长期运行

- 至少两名未参与实现的试用者，分别在干净 Linux／Windows 环境按文档完成安装；问题归入安装、平台授权、订阅或产品缺陷。
- 八渠道各完成真实私聊、连续消息、长文及其声称支持的媒体操作；主动发送和固定提醒仅对已验证可用的渠道验收。
- 连续观察至少七天，并观测到所支持订阅至少一次真实续订；租期超出观察窗口时延长观察或安排可控租期演练。
- 演练网关断线、Tunnel 中断、进程异常退出、网络超时、过期、满盘及升级失败。整机重启在获准的维护窗口验收。
- 演练新机器恢复及迁移互斥，检查原存储密钥、绑定、队列、去重、订阅与结果不明状态完整保留。
- 实测八渠道同时运行和媒体处理的资源占用，公布推荐配置及容量边界。RC 阶段只收缺陷修复和必要兼容性修复。

## 1.0 发布门槛

P0 包括凭据泄漏、越权／串会话、已确认状态损坏和自动重发结果不明消息。P1 包括已满足平台条件的基础接入、收发、订阅续期或恢复流程不可用。

- [ ] 八渠道基础私聊的真实验收完成，公开能力矩阵与实际结果一致。
- [ ] 无未解决的 P0／P1 缺陷；没有串会话、越权回复或自动重发结果不明消息。
- [ ] Linux／Windows 干净安装、常驻、重启、升级、回滚及完整状态恢复通过。
- [ ] 订阅到期与续订经过真实验证，长期运行观察通过。
- [ ] 每个组件固定 SHA、版本及哈希；所有必需 CI 和最终发行包验证通过。
- [ ] 双语安装、故障处理、能力与维护文档完成，第三方许可证及发行文件核对完成。

正式发布使用经验证的 `main` 提交和稳定标签构建。PR 按项目既定 Squash 流程合并；先发布共享 core 和渠道构件，再固定总包。渠道组件保留独立版本号。发行页提供包校验、组件与依赖清单、更新说明、已知限制和回滚说明，核对构建来源与第三方许可，生产凭据留在运行主机。

## 人工操作边界

平台登录／扫码／验证码、组织管理员授权、应用及长期凭据确认、本人配对，以及域名／证书／公网入口批准仍需账号主人参与。原 dot 的订阅使用真实流程产生的 callback。

Agent 优先使用 CLI、API、SSH 和文件完成配置、检查、打包及演练。确需 Computer Use 时明确范围并取得授权；工具无法访问的管理页面提供官方手动步骤和安全交接入口。人工消息验证使用普通内容，尽量集中完成。

## 新渠道如何进入总发行版

现有 `dot-lark-bridge`、`dot-qq-bridge` 和 `dot-bridge-core` 保持独立。各渠道仓库负责平台接入，`dot-bridge-core` 提供共享能力，`dot-bridge` 总仓库负责统一安装、配置和运行管理。用户可以只启用自己需要的渠道。

1. 新建独立 `dot-<渠道>-bridge` 仓库，完成平台绑定、收发、附件及平台限制处理。
2. 公共能力复用 `dot-bridge-core`；提供统一的组件导出和渠道能力说明。
3. 在总仓库登记固定版本，补齐配置入口、运行管理和组合测试。
4. 使用真实账号确认原 dot 收到消息、原会话只回复一次，以及重启恢复。
5. 完成后才加入 `channels` 命令与可启动配置。

平台 token 和 dot 的 Tunnel runtime key 是两种不同凭据。新增渠道不意味着改用模型 API，也不意味着更换原 dot。QQ 个人号 OneBot/NapCat 与已有的 QQ 官方机器人也是两种接入方式，应分开评估。
